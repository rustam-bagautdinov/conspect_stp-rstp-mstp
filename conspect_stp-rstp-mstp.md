# STP / RSTP / MSTP — конспект

> Базовые практические заметки по L2 spanning tree протоколам, диагностике в RouterOS и границам совместимости с другими вендорами.

---

## 1. Зачем нужен STP: проблема L2-петли

Ethernet изначально проектировался как protocol без петлевой защиты:

- **У Ethernet-кадра нет TTL** — в отличие от IP, кадр не "стареет" и не может быть отброшен по превышению числа хопов.
- Коммутатор **копирует кадр** с одного интерфейса на другой в трёх случаях: broadcast, multicast, unknown unicast (MAC не найден в таблице).

Если между двумя коммутаторами есть **два и более кабеля без STP или LACP**, получается следующая цепочка:

1. Два кабеля без STP/LACP объединяют коммутаторы в кольцо.
2. Кадр не имеет TTL — ничто не остановит его циркуляцию.
3. Broadcast и unknown unicast размножаются на каждом витке — трафик растёт лавинообразно.
4. MAC-адрес отправителя "прыгает" между портами в MAC-таблице (MAC flapping), т.к. один и тот же кадр приходит с разных портов.
5. Сеть перестаёт работать — broadcast storm кладёт CPU коммутаторов и полосу пропускания.

Для понимания того, как считается размер и "стоимость" кадра при диагностике петель, полезно помнить структуру Ethernet II:

- Преамбула (7 байт) и SFD (1 байт) относятся к **синхронизации на линии** и **не входят в размер кадра**.
- IFG (12 байт) — это **интервал между кадрами**, а не часть кадра.
- Размер кадра: **64–1518 байт без VLAN / до 1522 байт с VLAN (802.1Q, +4 байта)**.
- Поле 802.1Q (VLAN-тег) — опционально, 4 байта.

## 2. Методика выявления и локализации петли

Порядок действий при подозрении на петлю (от общего к частному):

1. **Физическая и логическая карта сети** — без неё локализация превращается в угадывание.
2. **Сегментное отключение групп устройств** — от "верхнего" уровня к "нижнему" (от ядра к доступу), наблюдая, когда пропадает симптом.
3. В идеале — **переход границы на L3**, чтобы физически ограничить домен broadcast/петли размерами одного L2-сегмента.

### Диагностика STP/RSTP в RouterOS

| Шаг | Действие | Команда RouterOS |
|---|---|---|
| 1 | Зафиксировать симптом (петля / потери / переключения) | — |
| 2 | Проверить bridge | `/interface bridge monitor bridge1` |
| 3 | Проверить порты | `/interface bridge port monitor [find]` |
| 4 | Проверить MAC-таблицу | `/interface bridge host print` |
| 5 | Захватить BPDU | `/tool sniffer quick` |

**Ключевые поля для анализа:**

- `root-bridge-id` — кто сейчас root;
- `root-port` — через какой порт путь к root;
- `role` / `forwarding` — роль и состояние порта;
- `actual-path-cost` — фактическая суммарная стоимость пути;
- `bpdu-tx-rx` — счётчик передаваемых/принимаемых BPDU;
- `topology-changes`, `last-topology-change` — история пересчётов дерева.

**Типовые проблемы:**

- неожиданный root (кто-то стал root вместо запланированного коммутатора);
- неожиданный discarding (порт, который должен быть forwarding, заблокирован);
- MAC flapping (адрес скачет между портами — признак петли);
- частые topology change (нестабильность физики или конфигурации).

Итоговая проверка — сравнить **фактическое дерево** с **деревом по проекту** (какие порты root/designated/alternate, где forwarding, где discarding).

### Дополнительно: HW offload vs STP/RSTP

На части устройств включение STP/RSTP/MSTP/VLAN-filtering **может отключать hardware offload** (аппаратную коммутацию через switch-chip/ASIC). Нужно заранее решить, что приоритетнее — защита от петель или производительность — и свериться с документацией на совместимость этих функций для конкретной модели.

- **Флаг H есть** → коммутация в switch chip (ASIC) — высокая пропускная способность, низкая нагрузка на CPU.
- **Флага H нет** → трафик идёт через CPU (bridging через процессор) — возможна высокая нагрузка на CPU, пропускная способность ограничена CPU.

Что проверить:
1. `/interface bridge port print` — какие функции реально включены;
2. фактический флаг **H** на порту;
3. конкретную модель switch chip;
4. поддержку RSTP/MSTP/VLAN-filtering именно этим чипом (не все switch chip поддерживают одинаковый набор функций).

## 3. STP (IEEE 802.1D) — классический вариант

**Назначение:** отключение избыточных соединений, если линк на порту "съедает" всю полосу пропускания (т.е. предотвращение петли ценой отключения резервных линков).

- BPDU (Bridge Protocol Data Unit — служебные кадры протокола) рассылает **только root bridge**.
- Скорость обнаружения проблемы и восстановления **низкая**: типовая сходимость дерева — **30–50 секунд**.
- Таймеры по умолчанию:
  - **Hello Time** — 2 сек (интервал рассылки BPDU от root);
  - **Forward Delay** — 15 сек (длительность каждой из фаз Listening и Learning);
  - **Max Age** — 20 сек (через сколько BPDU считается устаревшим).
- Состояний портов больше, чем у RSTP (5 штук): **Disabled → Blocking → Listening → Learning → Forwarding**.

---

## 4. RSTP (IEEE 802.1w) — Rapid Spanning Tree

**Отличия от STP:**

| | STP | RSTP |
|---|---|---|
| Кто шлёт BPDU | только root bridge | **каждый** коммутатор, каждые 2 сек |
| Роль BPDU | топология | одновременно и topology, и "keep-alive" устройства |
| Сходимость | медленная (30–50 сек) | быстрая (доли секунды — единицы секунд, через механизм proposal/agreement на point-to-point линках) |
| Состояний портов | 5 | 3 |
| Совместимость | — | **обратно совместим со STP** (может работать в смешанной сети, деградируя до STP-поведения там, где это нужно) |

Дополнительные RSTP-специфичные порты в RouterOS, влияющие на скорость сходимости: `edge` (порт к конечному хосту, сразу в forwarding) и `point-to-point` (включает быстрый handshake proposal/agreement).

### Роли и состояния портов RSTP

| Роль | Описание |
|---|---|
| **Root port** | Порт, смотрящий в сторону root bridge — лучший (по стоимости) путь к root. На не-root коммутаторе он один. |
| **Designated port** | Порт в сторону сегмента/другого коммутатора, "отвечающий" за пересылку трафика в этот сегмент — лучший порт сегмента. |
| **Alternate port** | Резервный путь **к root bridge** через другой сегмент/коммутатор — имеет более высокую стоимость/приоритет, чем root port, и остаётся в discarding, пока жив основной путь. |
| **Backup port** | Резерв **designated**-порта на **том же самом** сегменте (актуально, когда к одному разделяемому сегменту/хабу подключено два порта одного и того же коммутатора). |

### Состояния портов

| Состояние | Что происходит |
|---|---|
| **Discarding** | Данные не передаются (объединяет Blocking/Listening/Disabled классического STP) |
| **Learning** | Порт изучает MAC-адреса, но данные ещё не пересылает |
| **Forwarding** | Порт передаёт данные |

## 5. Выбор Root Bridge и приоритет

- Минимально необходимая настройка STP/RSTP — **указание root bridge**.
- По умолчанию root bridge выбирается по **наименьшему значению Bridge ID**, а Bridge ID = **Priority + MAC-адрес**. Если priority у всех одинаковый — решает наименьший MAC.
- Priority можно и нужно назначать **административно**, чтобы явно контролировать, кто станет root.
- Диапазон priority по стандарту 802.1D/w — **0–61440, шагом 4096** (16 возможных значений), значение по умолчанию — **32768 (0x8000)**.
- На практике (в т.ч. в RouterOS, где значение часто отображается в hex) администраторы двигаются в диапазоне **0x1000–0x8000**, где **0x8000 — наименее приоритетное** значение среди типично используемых (это же и есть дефолт "по умолчанию — не root"), а меньшие значения (0x1000, 0x2000...) явно назначают root/backup-root коммутаторам.
- Значение **0** технически допустимо, но **может вызывать аномалии** — на практике лучше его избегать.

При выборе root bridge дерево **перестраивается относительно root**: только тогда у портов появляются финальные роли и состояния (см. таблицы выше).

## 6. Path Cost — как RSTP выбирает путь

Путь к root bridge выбирается по **наименьшей суммарной стоимости (path cost)**, а не по количеству хопов.

**Стоимость по скорости линка (`port-cost-mode=long`):**

| Скорость | Cost |
|---|---|
| 10 Мбит/с | 2 000 000 |
| 100 Мбит/с | 200 000 |
| 1 Гбит/с | 20 000 |
| 10 Гбит/с | 2 000 |
| 25 Гбит/с | 800 |
| 100 Гбит/с | 200 |

Побеждает путь с **наименьшей суммарной стоимостью** (пример: путь в 1×1 Гбит/с = 20000 проигрывает пути 10 Гбит/с + 10 Гбит/с = 2000+2000 = 4000).

**Особенности в RouterOS:**

- **EoIP / VXLAN / WiFi** по умолчанию получают cost **20000** (как 1 Гбит/с), независимо от реальной пропускной способности — это надо учитывать при проектировании.
- **Bonding** — учитывается **наибольший** cost среди участников бонда (т.е. бонд не "суммирует" скорость для целей path cost).
- Фактическую стоимость пути смотреть в `actual-path-cost` в port monitor.

## 7. MSTP (IEEE 802.1s, позже включён в 802.1Q) — Multiple Spanning Tree

MSTP отвечает на главный недостаток RSTP: **один общий tree на всю L2-топологию** означает, что весь трафик всех VLAN идёт по одним и тем же (не)заблокированным линкам — балансировки нагрузки между VLAN нет, часть портов простаивает вхолостую.

**Идея MSTP:**

- VLAN группируются в **MST-инстансы (MSTI — Multiple Spanning Tree Instance)**; для **каждой группы VLAN** строится **своё** дерево (свои root/alternate/designated), что позволяет распределять трафик разных VLAN по разным физическим линкам.
- Коммутаторы, у которых совпадают три параметра — **имя региона (region name)**, **номер ревизии (revision)** и **таблица соответствия VLAN → MSTI** — считаются одним **MST-регионом**. Даже минимальное расхождение (например, разная ревизия) переводит коммутатор в другой регион с точки зрения протокола.
- Внутри региона все инстансы синхронизируются через **IST (Internal Spanning Tree)** — служебное дерево региона (по сути, инстанс 0/CIST-часть).
- Наружу, для соседних регионов и для RSTP-коммутаторов, **весь регион представляется единым виртуальным RSTP-мостом** — это и обеспечивает совместимость MSTP с "чистым" RSTP на границе.
- MSTP **обратно совместим с RSTP** (регион общается с внешним RSTP-коммутатором как единое целое) и, соответственно, транзитивно — со STP.

**BPDU:** MSTP использует тот же multicast MAC-адрес назначения, что и RSTP — `01:80:C2:00:00:00`, но с дополнительной служебной информацией (MSTI-конфигурация, digest таблицы VLAN) внутри BPDU.

**Итог:** MSTP = RSTP по скорости сходимости и логике ролей/состояний портов + возможность load balancing по VLAN, которой не хватает "плоскому" RSTP.

## 8. Границы совместимости: RSTP / MSTP / PVST и другие вендоры

| Технология | Что это | BPDU (MAC назначения) | Совместимость |
|---|---|---|---|
| **RSTP** (802.1w) | Одно дерево на всю L2-топологию | `01:80:C2:00:00:00` | ✅ RSTP ↔ RSTP — совместимо "из коробки" |
| **MSTP** (802.1s) | Разные деревья для групп VLAN, поддерживается RouterOS | `01:80:C2:00:00:00` | ✅ MSTP ↔ MSTP — совместимо **только при одинаковом регионе** (имя, ревизия, VLAN-map) |
| **PVST / Rapid-PVST** (Cisco, проприетарно) | Отдельное дерево для **каждого** VLAN | `01:00:0C:CC:CC:CD` | ⚠️ Другой протокол BPDU — RouterOS **не участвует** в PVST; требует отдельного проектирования границы. PVST BPDU может обрабатываться RouterOS просто как обычный multicast-кадр (т.е. будет прозрачно проходить/флудиться, а не осмысленно обрабатываться) |

**Правильно:** один bridge с `vlan-filtering=yes`, VLAN разведены через trunk/access-порты внутри одного STP/RSTP/MSTP-домена.

**Неправильно:** VLAN-интерфейс используется как порт другого bridge (bridge1 → vlan10 → bridge2) — это создаёт риск tagged BPDU и скрытых петель, т.к. STP-домены на самом деле не разделены так, как кажется из схемы.

### Аналоги у других вендоров (кратко)

| Вендор | Реализации | Комментарий по совместимости |
|---|---|---|
| **MikroTik (RouterOS)** | STP, RSTP, MSTP | Полностью стандартные 802.1D/w/s |
| **Cisco** | PVST+ / Rapid-PVST+ (проприетарно, per-VLAN дерево), MST (это и есть стандартный 802.1s) | PVST+/Rapid-PVST+ **не совместимы напрямую** со стандартным RSTP/MSTP (другой BPDU MAC) — нужна граница (Cisco обычно ставят "MST + PVST simulation" на границе). Cisco MST совместим с MSTP других вендоров при одинаковых region-параметрах |
| **Juniper (Junos)** | STP, RSTP, MSTP, VSTP | VSTP (VLAN Spanning Tree Protocol) — аналог PVST, один инстанс на VLAN, тоже требует границы, как и Cisco PVST |
| **HPE / Aruba (ProCurve)** | STP, RSTP, MSTP | Стандартные реализации, совместимы по стандарту |
| **Huawei** | STP, RSTP, MSTP | Стандартные реализации, совместимы по стандарту |

**Практический вывод:** стандартный **RSTP** и стандартный **MSTP** (при совпадающем регионе) — переносимы между вендорами. Проприетарные **PVST/Rapid-PVST (Cisco)** и **VSTP (Juniper)** — нет, и всегда требуют осознанного проектирования границы домена.

## 9. Как подключать внешний L2-канал (к другой площадке/арендодателю/партнёру)

| Вариант | Описание | Рекомендация |
|---|---|---|
| **1. L3-граница** | Между офисами — L3-маршрутизатор, разные подсети (напр. 10.0.0.0/24 и 172.16.0.0/24), маршрутизация между сетями, **BPDU не пересекают границу** | ✅ Рекомендуется |
| **2. Контролируемый L2** | Между офисами ходят конкретные VLAN, применяется политика L2 Shield: фильтрация BPDU, ограниченный список VLAN, root guard при необходимости, мониторинг topology change | ⚠️ Допустимо после проектирования |
| **3. "Слепой" bridge / L2-туннель** | EoIP/подобный L2-туннель между bridge двух офисов, broadcast свободно ходит в обе стороны | ❌ Не рекомендуется: неизвестная STP-топология на другой стороне, риск удалённой петли, риск захвата root чужим коммутатором |

**Чек-лист перед подключением внешнего L2-канала:**

1. Где находится root bridge (у себя или на другой стороне)?
2. Какие VLAN реально передаются через канал?
3. Передаются ли BPDU через канал (или фильтруются)?
4. Кто отвечает за поиск петли, если она возникнет на стыке?
5. Как канал мониторится (topology-changes, доступность, флаппинг)?

> Расширяющие broadcast-домен технологии (**EoIP / VXLAN / VPLS**) без должного контроля превращают "внешний" сегмент в часть своего L2-домена со всеми рисками петель — см. вариант 3.

## 10. Базовые дополнения: защитные механизмы порта

Не было в исходном конспекте, но напрямую относится к практической эксплуатации STP/RSTP:

- **Edge port** (аналог Cisco PortFast) — порт к конечному хосту (не коммутатору), сразу переходит в forwarding, минуя полный цикл согласования. В RouterOS — параметр `edge` (`auto`/`yes`/`no`) на bridge-порту. Если на edge-порту неожиданно приходит BPDU — это признак того, что туда подключили коммутатор, а не хост (потенциальный источник петли/чужого root).
- **Point-to-point** — параметр, включающий быстрый handshake proposal/agreement RSTP на full-duplex линках между двумя коммутаторами; на shared/half-duplex сегментах RSTP ведёт себя ближе к классическому STP по скорости сходимости.
- **BPDU Guard / Root Guard / Loop Guard** — общие 802.1-концепции защиты дерева (терминология и доступность конкретных параметров отличаются по вендорам, для RouterOS — сверяться с документацией на конкретную версию):
  - защита от появления **чужого root** на порту, который не должен его принимать;
  - автоматическое отключение порта, если на edge-порт пришёл BPDU;
  - защита от несогласованных состояний при частичной потере BPDU.

## 11. Глоссарий

| Термин | Расшифровка |
|---|---|
| **STP** | Spanning Tree Protocol, IEEE 802.1D |
| **RSTP** | Rapid Spanning Tree Protocol, IEEE 802.1w |
| **MSTP** | Multiple Spanning Tree Protocol, IEEE 802.1s (сейчас часть 802.1Q) |
| **PVST / Rapid-PVST** | Per-VLAN Spanning Tree — проприетарная технология Cisco, отдельное дерево на VLAN |
| **VSTP** | VLAN Spanning Tree Protocol — аналог PVST у Juniper |
| **BPDU** | Bridge Protocol Data Unit — служебный кадр протокола STP-семейства |
| **Bridge ID** | Priority + MAC-адрес коммутатора; определяет, кто станет root bridge |
| **Root Bridge** | Коммутатор с наименьшим Bridge ID — точка отсчёта для построения дерева |
| **Path Cost** | Суммарная "стоимость" пути до root bridge, зависит от скорости линков |
| **MSTI** | Multiple Spanning Tree Instance — отдельное дерево внутри MST-региона для группы VLAN |
| **CIST / IST** | (Common) Internal Spanning Tree — служебное дерево, связывающее регионы MSTP между собой / внутри региона |
| **MST-регион** | Группа коммутаторов с одинаковым именем региона, ревизией и таблицей VLAN→MSTI |
| **TCN** | Topology Change Notification — уведомление о смене топологии (классический STP) |
| **Edge port** | Порт к конечному хосту, минует полное согласование состояния |
